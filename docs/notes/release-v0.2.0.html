🚀 EventRunner7 - Release v0.2.0

What's new in v0.2.0?

Under the hood this is a big maintenance release: the rule engine has been reworked (modifiers are now proper gates, the rule lifecycle is explicit, and the test suite grew from 27 to 38 tests). Most of that is invisible — your rules behave the same, only better. Here is what concerns you as a user:

Fixed — things you may have noticed

  • single + since could get stuck: after a re-trigger cancelled a pending since-window, the rule never fired again. Windows now restart properly on re-trigger.
  • Very long since-windows (over 30 days) silently failed: an internal watchdog cut them off mid-window. Any length now works.
  • rule:terminate() did not fully terminate: interval rules kept ticking and late callbacks could still wake up an old run. It now really stops — timers cancelled, interval stopped, stale callbacks discarded.
  • Disabled rules kept consuming timers in the background: interval rules ticked forever while disabled. disable() now stops the interval scheduler; enable() resumes it — clock-aligned intervals continue at the next exact boundary, relative ones restart from the enable time.
  • One runtime error killed a rule permanently: a single failed HTTP call or an offline device disabled the rule until you re-enabled it manually. New disableOnError option — disableOnError=3 disables only after 3 consecutive errors, disableOnError=false never disables. The default is unchanged.
  • Errors at registration are now reported clearly: eval returns nil plus an error message, so scripts can tell "failed" from "still running".

New for rule authors

  • rule:recompile() — rebind a single rule in place: rule("dID = 88"); r = rule("dID:value => log('hupp')"); dID = 99; r:recompile() — now it listens to device 99, without restarting the QA or resetting all rules.
  • rule:state() and rule.active — ask a rule whether it is enabled/disabled and how many runs are in flight; info() shows it as well.
  • Stricter rule heads — side-effecting or unknown functions in a condition now fail at registration instead of misbehaving mysteriously later. log() still works as a debug probe; whitelist your own helpers with: fibaro.ER._headFuns.myFun = true
  • Modifier combinations documented — a full semantics table lives in RULES.md, and the parser now rejects two combinations that never worked: duplicate modifiers (cooldown 3 cooldown 5) and single/debounce together with first_in.

If you are updating

  • Rules that call impure functions in conditions will now fail at registration — whitelist the helper or move the call into the action.
  • The rejected combinations above now give an error at registration instead of misbehaving silently.
Docs: RULES.md, EventScript.md and AST_Format.md are updated, and the architecture reviews now live in docs/reviews/.
